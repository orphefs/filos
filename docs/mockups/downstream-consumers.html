Who does this change reach outside the repo?

Filos looks for downstream consumers with GitHub code search, but only when you ask it to. It narrows the search before reading anything and judges matches from the short fragments search returns. It never clones or reads whole downstream codebases, and it says plainly what it couldn't check. These screens use the bundled sample PR, so every repo and line here is example data.

Narrow first, read as little as possible

Each stage shrinks the search space before the next one spends anything. GitHub's search API has no regex and ignores punctuation such as . ( / @, so it matches words. The narrowing comes from words, file names and repos. The agent tells calls from mere mentions by reading the fragments search returns.

Dependents first. One search of package.json files turns "all of acme" into a short list of repos. Every later search stays inside that list.
Fragments, not files. GitHub returns short fragments around each match (at most two per file), so most matches are judged without fetching anything. A file window of about 60 lines is fetched only when the agent asks, within the budget.
Gaps are found, not assumed away. Inactive repos fall out of GitHub's search, so they are checked by reading their package.json directly. A repo found this way is shown as not searchable, never as safe. Only default branches are searchable.

Decisions

Settled

  • Live GitHub code search, with no index and no clones. The scope is the PR's owner by default, excluding the PR's repo, and more owners can be added.
  • Filos runs the searches. The agent proposes follow-ups within a cap and never gets network access.
  • It runs only when you click Search GitHub; Skip goes straight on.
  • Questions wait for the downstream findings, or for Skip.
  • A privacy notice appears before the first search in each org.
  • Repos GitHub can't search are detected and shown as not searchable, never as safe.

Still open: easier to decide after trying it

  1. Budgets. Proposed: 15 searches (including one probe per dependent found outside search), 30 file windows of about 60 lines, 3 rounds, and up to 4 follow-ups per round. More finds more but takes longer, since GitHub allows about 10 searches a minute.
  2. Verdict words. Proposed: Breaks, Changes behaviour, Unaffected and Not searchable, each with a confidence. Alternatives: Breaking, Affected, Safe and Unknown. Or a 0–1 impact score.
  3. How much an unsearchable dependent weighs in the risk colour. Proposed: as one possible consumer. Or as a full consumer, or not at all, with only the warning.
  4. Callers with no package dependency, such as services that call the PR's API over HTTP. Proposed: search route and message names across the whole org, skipping the dependents step. These searches are broader and less precise, and they use more of the budget.
  5. Finding dependents search can't see. Proposed: list the org's repos and read the root package.json of those with no push in a year, up to a cap (say 50 repos). Large orgs with many inactive repos would hit the cap, and Filos would say so.
